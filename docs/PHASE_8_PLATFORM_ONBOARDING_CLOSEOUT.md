# Phase 8 — Platform administration and onboarding closeout

## Scope delivered

### 8A — Platform administration console
- Restricted `/platform` console for business directory, user directory and append-only audit history.
- Account status changes require a reason and use the existing server-side super-admin authorization.
- The browser never decides whether an operator is a super-admin.

### 8B — Business workspace provisioning
- `POST /api/v1/platform/businesses` provisions a business for an already-registered active user.
- The transaction creates the business, initial branch, owner membership, owner-to-branch assignment and default expense categories together.
- A platform audit event records the actor, reason, owner user ID, branch ID and currency.
- Provisioning rejects missing/inactive owner accounts and invalid inputs. It does not create passwords, change platform roles, or send credentials.

### 8C — Operator workflow
- The console includes a provisioning dialog with required business name, initial branch, existing owner email, ISO-style three-character currency code and reason.
- Successful creation refreshes the business directory. Failure is surfaced without claiming success.
- Existing account suspension/reactivation and audit views remain available.

### 8D — Security and operational boundaries
- Every platform endpoint remains behind database-backed active-super-admin authorization.
- Workspace creation uses transaction-local registration/user/business context to satisfy existing RLS policies; owner lookup uses the existing narrow authentication lookup function and then locks the owner row under self scope.
- Owner account must be active. Platform role is never modified.
- No platform endpoint exposes tenant sales, inventory, customer or financial records.
- No invitation token or password is generated by the provisioning operation. The designated owner must already have a valid MEKU-In account and signs in normally.

## Explicitly not included
- Email-based first-user invitations, token redemption, or password setup for people without accounts.
- Subscription billing, plan enforcement, payments, ownership transfer, tenant impersonation, tenant data editing/deletion, or super-admin promotion.
- Those capabilities require separate product rules, delivery configuration, and security review; they are not inferred by this phase.

## API contract

`POST /api/v1/platform/businesses`

Request:

```json
{
  "name": "Harbour Kitchen",
  "branch_name": "Main Branch",
  "owner_email": "owner@example.com",
  "currency": "KES",
  "reason": "Approved customer onboarding case"
}
```

Success (`201`) returns `business_id`, `branch_id`, `owner_user_id`, and `status`. The response contains identifiers only; no credentials or session are issued.
